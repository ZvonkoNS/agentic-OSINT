### 9.1 Scope and input validation

**In scope:** classification (public/private/reserved/CGNAT); RDAP registration of the netblock and abuse contact; ASN and routing (current and historical announcement); reverse DNS; geolocation estimates from at least two providers; Tor exit status now and at the incident time; VPN/hosting/proxy indicators from registration data; passive exposure data from a public index; public reputation/blocklist listings.
**Out of scope (→ Leads or prohibited):** any packet sent to the address itself (ping, traceroute, port scan, banner grab, an HTTP request addressed to the bare IP). The passivity line in this suite is: visiting a published website by its name, as any visitor does (L1-WEB, L1-DOM), is permitted; addressing a host by its IP to see what answers is probing, and is not. Subscriber identification is a lawful request to the operator (Lead); domains hosted on the IP beyond passive listings are L1-DOM runs.

Validation (in code if CAP-CODE, `ipaddress` module):
- Valid IPv4/IPv6 syntax; normalise IPv6 to compressed form, record as given.
- If private (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`), loopback, link-local, multicast, reserved, or CGNAT (`100.64/10`): the address is not globally unique and cannot be attributed on the public internet; the run ends as `NOT-INVESTIGABLE` (core §3.1) with a short pack stating that fact.
- The **incident timestamp** comes from intake field 16. If it was given without a time zone, validation asks for UTC at intake. If it was not provided at all, do not stop: run the time-dependent checks (S6 historic Tor, S3 routing history) for "now" only, flag this in Findings and Limitations, and note that the run can be repeated with the timestamp.

**Intake additions (printed with the form):** field **16** = "Incident date and time in UTC (the moment the IP was observed in the case)". Authorisation **D: none**.

### 9.4 Task-specific capture rules

- **Never touch the host.** No ping, traceroute, port scan, TLS handshake, HTTP GET to the IP, or any tool that does these (nmap, masscan, curl to the IP). All exposure data comes from third-party passive indexes and is labelled with their observation date.
- Time dependence is central: every finding is "as at <UTC>"; the incident timestamp is used for routing history and historic Tor checks, and the report states explicitly that assignment of the IP to a subscriber at the incident time is only obtainable from the operator (Lead: abuse/legal contact from S2).
- Geolocation providers give estimates with their own methodology; capture the raw JSON, record provider and timestamp, and never present a city as a fact.
- Tor bulk-exit list is current only; ExoneraTor answers for a date; capture both with timestamps.
- InternetDB fields (ports, CPEs, vulns tags) are Shodan's historic observations; do not restate them as current facts and do not treat "vulns" as verified.
- Abuse contacts are recorded for the lawful-request path; no email is sent by this agent.

### 9.5 Task-specific self-healing cases

| Symptom | Remedy to propose at G4 |
|---|---|
| rdap.org bootstrap fails | Query the RIR's own RDAP service directly: ARIN `https://rdap.arin.net/registry/ip/<ip>`, RIPE `https://rdap.db.ripe.net/ip/<ip>`, APNIC `https://rdap.apnic.net/ip/<ip>`, LACNIC `https://rdap.lacnic.net/rdap/ip/<ip>`, AFRINIC `https://rdap.afrinic.net/rdap/ip/<ip>`; RIPEstat `whois` as a labelled secondary source |
| Geolocation providers disagree on country | Add a third HTTPS provider (level B) if available; report the disagreement; no adjudication |
| ExoneraTor has no data for the date | Record "no data for date"; use routing history and holder type as the only indicators |
| InternetDB returns 404 | Record "no Shodan passive data" (normal for many IPs) |
| AbuseIPDB / Spamhaus block automation | DEFERRED (post-run manual lookup) |
| GreyNoise / reverse-IP listings unreachable | SKIPPED (optional context) |
| Timestamp ambiguity discovered mid-run (e.g. two timestamps in field 7) | Use the one in field 16; record the other in Limitations; do not ask mid-run |
| IPv6 address belongs to a /64 with privacy extensions | State that the host part is likely temporary; attribution is at prefix level |

### 9.6 Findings structure

1. **Address classification** — type, normalised form, globally routable Y/N, incident timestamp used.
2. **Registration** — netblock, holder, country of registration, abuse contact, dates (EV refs).
3. **Routing** — ASN/AS name now and at the incident time; prefix; changes noted.
4. **Reverse DNS** — PTR values and agreement.
5. **Geolocation estimates** — per-provider table; consensus statement at country level only.
6. **Anonymisation indicators** — Tor now / at date (facts, EV refs). Under the heading **Analysis (outside ISO/IEC 27037 — opinion)**: hosting/datacenter/VPN indicators with the captured basis for each.
7. **Passive exposure** — Shodan/urlscan observations with their dates.
8. **Reputation listings** — as shown, labelled third-party.
9. **Hostnames observed** — passive listings, as Leads.
10. **What this report cannot say** — subscriber identity, device, physical location of a person.

### 9.7 XLSX sheets

`IP_Classification` (field, value) · `Registration_RDAP` (field, value, source, EV) · `ASN_Routing` (timestamp, ASN, AS name, prefix, source, EV) · `Reverse_DNS` (source, PTR, UTC, EV) · `Geolocation_Estimates` (provider, country, region, city, lat/long, ASN type, UTC, EV) · `Anonymisation_Checks` (check, date basis, result, source, EV) · `Exposure` (source, observation date, ports/services/tags, EV) · `Reputation` (source, count/category, latest date, EV) · `Hostnames` (hostname, source, date, EV).

### 9.8 Interpretation cautions

- An IP address identifies a network interface or a NAT gateway at a point in time, not a person or a device; many users can share it (CGNAT, VPN, corporate egress, Tor).
- Geolocation is an estimate of the network's registered or inferred location; errors of hundreds of kilometres are common, and VPN/hosting IPs geolocate to the datacenter.
- A Tor exit or VPN result means the originating user is unknown without further lawful process; it is not evidence of intent.
- Blocklist and abuse reports are third-party submissions about traffic from the IP, which may have come from other users of the same address.
- Passive exposure data reflects scans by a third party at an earlier date, not the current state.

### 9.9 Leads policy

Operator/abuse contact for the lawful request (with the incident timestamp and time zone to cite); hostnames observed (L1-DOM); related prefixes of the same holder; the originating service if a VPN/hosting provider is named (lawful request path).
